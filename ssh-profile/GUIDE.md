# Подробное руководство ssh-profile, схема версии 1

Файл `server-access.local.yml` в этой папке описывает персональное подключение.
Переносите весь каталог `ssh-profile/`, затем заново проверяйте доступ.
Начните с [README.md](README.md); инструкция модели — [AGENTS.md](AGENTS.md).
Профиль **не является секретом аутентификации**:
без соответствующего ключа в работающем SSH-agent профиль не предоставляет доступ.

## Состав

Шаблон: `server-access.example.yml` в этой папке (placeholders намеренно невалидны).

- `version: 1` — версия схемы; неизвестные поля и дубли YAML-ключей запрещены.
- `server.name` — безопасный локальный alias сервера.
- `server.host`, `server.port` — IP/DNS и порт.
- `ssh.user` — персональный либо явно подготовленный служебный аккаунт, не root.
- `ssh.authentication.method: agent` — закрытые ключи используются только через агент.
- `ssh.authentication.key_fingerprint` — SHA256 fingerprint **ключа пользователя**.
- `ssh.verification.policy: strict` — проверка ключа сервера обязательна.
- `ssh.verification.host_public_key` — полный доверенный **публичный ключ сервера**.
- `privileges.method: sudo`, `password_required: false` — ожидается рабочий `sudo -n`.

Профиль не содержит паролей, закрытых ключей, сокета агента, локальных путей,
команд оболочки, proxy settings или произвольных переменных Ansible.
SSH certificates/FIDO-ключи и host CA пока не поддерживаются; допускаются Ed25519,
RSA от 2048 бит и ECDSA nistp256/384/521. Для RSA не включается устаревшая SHA-1 подпись.

Файл содержит сведения об инфраструктуре. `*.local.yml`/`*.local.yaml` исключены из
Git собственным `.gitignore`, который переносится вместе с папкой.
В принимающем проекте отдельно исключите из Git runtime `temp/` и `.venv/`.
Передавайте профиль доверенным способом: замена адреса и доверенного host key
способна направить оператора на другой сервер. Наличие схемы не доказывает
подлинность самого переданного файла.

## Зависимости и границы

- Python 3.11+, PyYAML (`requirements.txt` в этой папке).
- Linux/WSL и OpenSSH (`ssh`, `ssh-add`, `ssh-keygen`) для операций с сетью.
- Native Windows поддерживает только `validate`.
- Выполняйте команды **из корня текущего проекта**. Пути входных файлов должны
  оставаться внутри него, включая разрешённые symlink; `.env*`, `*.pem`, `*.key`
  как входные файлы отвергаются. `.env` автоматически не загружается.
- Все производные и временные файлы создаются внутри `./temp/` и не являются
  переносимым контрактом. Исходный профиль не ссылается на них.
- Скрипт не устанавливает зависимости, не открывает другие проекты, не меняет
  `~/.ssh/config`, глобальный known_hosts или конфигурацию SSH сервера.

Все файлы подключения уже находятся в `ssh-profile/`. Установите зависимости
из `ssh-profile/requirements.txt` в `.venv` принимающего проекта, используя
project-local TMPDIR/TMP/TEMP и pip cache. Утилита не импортирует bootstrap-роли
и не обращается к исходному репозиторию. Готовый профиль автоматически находится
рядом со скриптом, поэтому при переносе его путь не нужно задавать заново.

## 1. Экспорт нового профиля (обычно не требуется при переносе готовой папки)

Запускайте в WSL-терминале, где работает SSH-agent с вашим персональным ключом:

```bash
python ssh-profile/server_access.py export \
  --name test-server \
  --user admakh \
  --key-fingerprint 'SHA256:ОТПЕЧАТОК_КЛЮЧА_ПОЛЬЗОВАТЕЛЯ' \
  --known-hosts temp/trusted_known_hosts \
  --output ssh-profile/server-access-next.local.yml
```

Если `--host`/`--port` отсутствуют, используются `BOOTSTRAP_HOST` и
`BOOTSTRAP_PORT` из уже загруженного окружения (порт по умолчанию 22).
Можно указать `--host` и `--port` явно. Значения подключения и ключи не выводятся
в журналы. Пароли bootstrap не используются и не передаются дочернему SSH.

Вместо `--key-fingerprint` можно указать `--team-file` с локальным YAML-документом
`users: [{username: ..., ssh_keys: [...]}]` внутри текущего проекта. Тогда выбирается
ровно один ключ указанного активного административного участника, доступный в агенте.
При нескольких подходящих ключах задайте fingerprint явно. Список команды не нужен
для последующего check/ansible и не входит в переносимую папку. Ключи и комментарии
из агента не печатаются.

Источник host key — уже доверенный project-local `known_hosts`, обычный или
с хешированными именами хостов. При нескольких алгоритмах предпочтение отдаётся
Ed25519, затем ECDSA, затем RSA. Конфликтующие ключи одного типа, `@revoked` и
`@cert-authority` требуют ручного разбора; автоматически не принимаются.

**Файл создаётся только после успешного реального входа по выбранному ключу,
проверки имени пользователя и `sudo -n id -u`.** Парольный fallback запрещён.
Существующий профиль не перезаписывается: для новой версии задайте новое имя,
например `ssh-profile/server-access-next.local.yml`, и замените старую версию
осознанно. Без `--output` целевой файл — `server-access.local.yml` рядом со скриптом.

## 2. Проверка в любом проекте

```bash
# Только схема, без сети и без агента:
python ssh-profile/server_access.py validate

# Реальный вход, проверка пользователя и sudo; без настройки сервера:
python ssh-profile/server_access.py check
```

SSH использует только выбранный ключ агента и отдельную сгенерированную
конфигурацию: strict host checking, pinned host key, запрет паролей, forwarding,
proxy и повторного использования ControlMaster. Стандартные приватные ключи
из `~/.ssh` не читаются. Публичный ключ-селектор и known_hosts удаляются после проверки.

Проверки выполняют только `id -un` и `sudo -n id -u`. Возможны обычные записи
аутентификации в системном журнале сервера; настройки, аккаунты и службы не меняются.
Проверка sudo подтверждает выполнение этой команды от root, а не полный аудит
разрешённых команд sudoers. Проекты должны обрабатывать отказ своих операций отдельно.

## 3. Адаптер Ansible

```bash
python ssh-profile/server_access.py ansible --output-dir temp/ssh-profile-session

# Только проверка подключения, без повышения прав:
ansible all -i temp/ssh-profile-session/inventory.yml \
  -m ansible.builtin.command -a '/usr/bin/id -un'

# Отдельная проверка sudo:
ansible all -i temp/ssh-profile-session/inventory.yml \
  -m ansible.builtin.command -a '/usr/bin/id -u' --become

# Затем — разрешённые задачи конкретного проекта:
ansible-playbook -i temp/ssh-profile-session/inventory.yml path/to/project-playbook.yml
```

Генерация сначала повторно проверяет живое подключение. Выходной каталог должен
быть новым и находиться в `temp/`. Получаются четыре файла: `inventory.yml`,
`ssh_config`, `known_hosts`, `identity.pub` — последний содержит только публичный ключ.
По умолчанию `--output-dir` равен `temp/ssh-profile`. Для другого профиля можно
явно передать `--profile ssh-profile/другой.local.yml`.

Inventory задаёт соединение, пользователя и метод sudo, **но не включает become
для всех задач** и не содержит паролей. Повышение привилегий выбирает playbook
либо оператор через `--become`. Для конкретных групп playbook создайте группы
поверх сгенерированного host alias; генератор не назначает серверу роли приложений.

Артефакты имеют локальные пути. Не переносите их в другой проект или на другой
компьютер — переносите папку ssh-profile и заново запускайте адаптер. После изменения порта,
пользователя или host key профиль и артефакты нужно осознанно обновить.
Inventory не защищает от намеренного переопределения его параметров в playbook/
extra-vars: принимающий проект и запускаемые задачи тоже должны быть доверенными.

## SSH-agent между терминалами

`SSH_AUTH_SOCK` — локальная настройка процесса, она не переносится в профиле.
Предпочтительно выполнять экспорт, проверку и Ansible из одного терминала WSL
с уже работающим агентом.

Для автоматизированного запуска допустим параметр:

```bash
python ssh-profile/server_access.py check \
  --agent-socket-file temp/ssh-agent-socket.txt
```

Файл содержит только путь к сокету. Утилита использует его для своего процесса,
но не изменяет окружение родительского терминала. Для последующего запуска
Ansible `SSH_AUTH_SOCK` должен быть доступен и тому процессу. Не копируйте socket
reference на другой компьютер и не пересылайте агент на сервер: forwarding отключён.
Не помещайте socket reference внутрь переносимого каталога: это runtime текущего
проекта. Для проверки готового профиля исходные BOOTSTRAP-пароли не нужны.

## Автоматизация доверия

Повторное ручное принятие fingerprint в каждом проекте не требуется: known_hosts
генерируется из доверенного публичного ключа внутри профиля. Автоматического
`ssh-keyscan` с принятием найденного ключа нет — сеть не является источником доверия.
При переустановке сервера несовпадение ключа останавливает работу.

Первичное получение host key из доверенного API провайдера либо переход на host
certificates/SSH CA — отдельное будущее улучшение, не часть версии 1.
